> **起因**：業主經常要求更新交流會場次、工作坊、首頁輪播海報，日後還要發部落格、新增影片頁；現行「業主傳訊 → 開發者改程式 → 部署」慢且易漏改。

## 一、設計原則

1. **職責分工**：內容品質由業主方負責，開發端不審查；發布即上線，不設審核（開發窗口 2026-11-17 確認）。
2. **商業營運優先於技術一致性**：要不要遷移，看它**是否正在妨礙營運**，不看技術是否整齊；運作正常、業主已習慣的系統（星靈出攤）延後。
3. **內容於建置時寫入 HTML**：可被搜尋引擎收錄、訪客無載入等待、網頁顯示不依賴 Google。
4. **壞掉也不能讓網站變糟**：建置失敗時維持上一版並通知開發者（第七節）。
5. **表單先擋錯**：能用必填、日期選擇器、下拉選單擋的錯誤在後台擋；建置時再以 Content Collections schema 做第二道驗證。
6. **紀錄可追溯**：每次發布是一筆 git commit（發布者、時間、改動），可還原。
7. **先有畫面，再做模組**：新內容類型先以寫死資料的版型給業主確認（開發端維護內容），確認後才做 CMS 模組。
   理由：沒有參考物就定欄位，日後改版面時後台欄位與已發布內容都要一起改。部落格與工作坊畫面已上線並經業主檢驗，不受此限。

## 三、分階段範圍

排序原則：**先做業主「原本做不到、現在自己能做」的，最後才動他們已經習慣的工具。**

### 第一階段：部落格、主題工作坊
- 目前都要找開發者修改，業主沒有既定習慣，CMS 是新增能力而非改變習慣。
- 同時驗證整套流程：登入、發布、自動部署、建置失敗通知。
- 順帶完成編輯者 GitHub 帳號申請與教學（開發窗口負責）。

### 第二階段：輪播海報、交流會場次、影片頁
- **首頁輪播列為第一項，先不做下架日期**：維持現行「人工刪除即下架」，下架日期日後再加。
  理由：第一階段要先打通流程，範圍越小越好；輪播須合併網站 repo 的保底圖（DEC-086）與內容 repo 的海報，
  是第一個跨 repo 拼接資料的地方，宜在流程穩定後再做。
- 交流會需要下架日期（第五節第 6 小節）。
- **影片頁分兩步**（第一節第 7 點）：
  1. **版型（不依賴 CMS，可提前）**：資料寫在頁面開頭的資料陣列（比照現行工作坊），欄位比照第五節第 5 小節，日後搬成內容檔不必改版面；
     頁面設 `noindex`、不加入導覽列，以直接網址給業主確認（比照 `/tarot`，DEC-073）。
  2. **CMS 模組**：業主確認後，決定導覽列名稱與位置、立 DEC（新路由屬 IA 變更），再把資料陣列遷移為 CMS 內容。

### 第三階段：星靈出攤
- 現行試算表使用頻率高、業主已用熟；編輯者熟悉 CMS 後再遷移，以免反彈、因小失大。
- 遷移後退役 `PUBLIC_BOOTH_API_URL` 與出攤用 Apps Script，改寫 `booth-plan.md`。
- 時效從「改完重新整理即生效」變為「發布後數分鐘」，遷移前須確認業主接受。

### 第四階段：課程許願池（視使用情況）
- 截至 2026-11-17 無人投票，載入慢（約 2～3 秒，Apps Script 冷啟動加 302 轉址）不構成營運問題。
- **若遷移**：課程清單 → CMS；投票 → VPS Node 服務新增投票 API＋SQLite（沿用 DEC-073 架構）。
  票數不重要：換課時從 0 計、以 CMS 課程編號為鍵、不搬舊票，因此不需嚴謹備份。
- **不採部分遷移**（只搬清單、投票留試算表）：兩邊課名不一致會計票錯誤。
- 若長期無人使用，請業主評估保留，或改成「想上這門課，私訊我們」的 LINE 按鈕（商業判斷）。

## 六、編輯者權限與安全（方案 C）

**問題**：Git-based CMS 以 GitHub 帳號登入，編輯者須持有 repo 寫入權；**寫入權以整個 repo 為單位，等於能改網站程式碼**。約 10 位編輯者，一人誤操作就可能改壞程式。

**採用方案 C：內容獨立 repo**。排除的方案（詳細比較見驗證紀錄）：
- **A. CMS 自有登入**（CMS 代為提交）：可行的 CMS 各有缺點（第九節）。
- **B. GitHub 路徑限制**：push ruleset 只開放給付費 Team 方案的私有 repo，本站網站 repo 為免費帳號的公開 repo，不可行。
- **同一 repo 的內容分支**：編輯者可推送到任何分支，包括修改 GitHub Actions workflow，進而讀到 repo 機密（如部署金鑰）。

### 架構
- **網站 repo**（公開，開發窗口 2026-11-17 確認）：程式碼，只有開發者有寫入權。
- **內容 repo** `starwoven-studio/starwoven-content`（2026-11-24 建立）：只放 CMS 管理的內容檔與圖片，編輯者只拿這個 repo 的寫入權。
  - **私有**：免費方案的私有 repo 也能邀協作者；編輯者帳號名、誤貼的個資、草稿不會公開。
    但提交過的內容仍永久留在歷史中，誤貼個資仍列教學重點。
  - **建在免費 GitHub 組織 `starwoven-studio`**，不放個人帳號下（`starwoven` 已被他人使用；名稱不綁 `.xyz`，因網域可能更換）：
    - 組織設定：Base permissions＝No permission、成員不得建立 repo。
    - 業主接手時加為組織擁有者即可，路徑與設定不變；換開發者時新人加入、原開發者退出。網站 repo 日後也可移入（第十二節）。
    - 2027 年公司註冊後，組織改為企業歸屬並加業主為擁有者。
- **效益**：編輯者誤操作碰不到程式碼；上傳圖片只讓內容 repo 變大（第八節）；內容提交不進網站 repo，開發者工作方式不變（第七節第 2 小節）。
- **代價（皆在開發端）**：建置與本機開發都要先取得內容 repo（第七節第 3 小節）；既有部落格 5 篇與封面要搬家；
  修改內容欄位（schema）時須同步更新內容 repo，不符的內容會在建置時被擋下（維持原站並通知），不會默默壞掉。

### 內容 repo 的安全措施（2026-11-24 定案）

前提：**編輯者帳號可能被盜**。目標是損害只限於「內容被亂改」（可從 git 歷史還原），不擴及訪客、伺服器與機密。
判斷原則：**能復原的壞掉從簡處理；不能復原的（資安、外洩）事先防範。**

1. **只接受 `.md`，不接受 `.mdx`**：MDX 可在建置時執行程式。Content Collections 只讀 `*.md`，Sveltia 設 `extension: md`。
2. **內文不得含原始 HTML**：`.md` 的原始 HTML（`<script>`、`<iframe>`、`onerror=` 等）會原樣輸出，在訪客瀏覽器執行。
   - 以 Markdown 解析結果檢查（**不用字串比對**，寫法變化太多）；出現原始 HTML 節點 → **建置失敗**（不默默刪除），網站維持上一版。
     **不設白名單**，`<strong>` 也不放行：編輯者不會手打 HTML，出現即視為帳號被盜。
   - **Markdown 引擎改用 `unified()`（`@astrojs/markdown-remark`）＋`remark-cjk-friendly`**（2026-11-24 定案）：
     Astro 7 預設引擎 satteri 無法辨識緊貼全形標點的粗體／斜體（`**「…」**` 會原樣露出星號），也無法以外掛修正；
     換引擎＋外掛後已實測正常，英文不受影響。編輯者按粗體按鈕即可，不需知道此限制。
     效能代價只在建置時；換引擎後須確認標題錨點、程式碼上色、內文圖片最佳化仍正常，並實測 Sveltia 粗體輸出的寫法。
   - 連結與圖片網址只允許 `https://`、`mailto:`、`tel:`、站內路徑（擋 `javascript:`、`http://` 等；2026-11-24 定案加入 `tel:`）。
   - 須先解決 Sveltia 插圖輸出 HTML 的問題（第十三節第 2 點），否則編輯者正常操作就會建置失敗。
   - YouTube 改用專門欄位（第五節第 2 小節）。
   - CSP（瀏覽器端第二道防線）暫不做。
3. **Sveltia 設定檔放網站 repo**（`public/admin/config.yml`）：編輯者改不到表單驗證；表單與 `content.config.ts` 同 repo、一起改一起上線。
   該檔必然公開（瀏覽器須讀取），**不得放任何密碼或金鑰**。網站 repo 維持公開（2026-11-24 掃描全部歷史，未發現機密）。
4. **VPS 以唯讀 deploy key 拉取內容 repo**：只開這一個 repo、唯讀、不綁個人；不用個人權杖。
   鑰匙由建置帳號產生、不得進任何 repo；列入第十二節第 7 項歸屬清單（位置、外洩時更換步驟）；重建 VPS 時重新產生並登記。
5. **以非 root 專用帳號建置**（第七節第 4 小節）：圖片處理程式若有漏洞，特製圖片可能在建置時執行程式；專用帳號讀不到 `/etc/starwoven/app.env` 與同機其他服務。
6. **建置前檢查內容 repo 不含符號連結**：防止以捷徑檔讀取伺服器上的機密檔。
7. **組織強制成員開啟兩步驟驗證**：正式邀請編輯者時開啟。

技術上無法防範的：帳號被盜後改文字、放詐騙連結、換圖片。靠兩步驟驗證、git 歷史還原與編輯者教學（不貼來路不明的連結與嵌入碼）。

### Repo 拆分原則（適用於日後所有模組）

- **依「部署或權限的邊界」拆，不依「功能」拆，也不提前拆。** 符合任一項才拆：
  1. 由不同的人修改（例：內容 → 內容 repo）；2. 部署方式或時機不同（例：常駐伺服器的論壇、購物後台）；3. 技術完全不同。
- **資料庫不做獨立共用模組**：資料庫屬於使用它的服務，共用等於重新綁在一起。
- **AI 抽卡服務現階段不拆**：前台用網站共用版型，本屬網站；前後端共用 `src/lib/ai/shared/`、同一開發者、流量不大，拆開要多維護一套建置部署、前後端分開協調，效益不明顯。
  - **重新評估時機**：需要會員帳號、付費或儲存使用者資料（需要資料庫）、改由不同開發者負責、部署互相干擾到影響營運、需要不同技術或機器。功能「數量」變多不構成理由。
  - **預留拆分**：新增 AI 功能遵守 `ai-platform-plan.md` 第十節檢查清單，日後要拆就是整個資料夾搬出。

**資料夾結構**：工作區頂層 `starwoven-workspace/` 本身不是 git repo（避免巢狀 git），其下並排 `starwoven-website/`、`starwoven-content/`（詳見工作區 `AGENTS.md`）。
VPS 現為 `/root/.openclaw/workspace/starwoven-workspace/`，部署改造時搬至 `/srv/starwoven-workspace/`（第七節第 4 小節）。跨 repo 一律用相對路徑。

## 七、部署流程

### 1. 流程與觸發
```
編輯者在後台按「發布」
  → CMS 提交 commit 到內容 repo
  → VPS 每 5 分鐘檢查一次（systemd timer），發現新 commit
  → VPS：拉取內容 repo → 建置 → 結構檢查 → 同步靜態網站
  → 約 6～7 分鐘內上線（最多等一輪檢查＋可能跳過一輪的 1 分鐘＋建置時間）
```

**觸發方式：VPS 定時檢查（2026-11-24 定案）**——只由 VPS 往外連，不開新的對外入口，也不在 GitHub 存放 VPS 的鑰匙。
- **不用 GitHub Actions**：設定檔須放在內容 repo，編輯者有寫入權，可改寫設定檔竊取存在 GitHub 的 VPS 登入鑰匙。
- **不用 webhook（暫不需要）**：VPS 須對外開放接聽網址並正確驗證簽章，多一段要維護、可能寫錯的程式。日後嫌慢可加 webhook 呼叫同一支腳本，其餘不變。
- 每次先以 `git ls-remote` 比對版本號（數 KB），有新 commit 才拉取與建置；建置次數取決於發文量，與間隔無關。
- systemd timer：輪詢 timer 設 `AccuracySec=1s`（預設 1 分鐘，會延後觸發）；每日重建 timer 用 `OnCalendar=` 加 `Persistent=true`（關機錯過時開機補跑）。

### 2. 兩套部署腳本

| | 程式部署（`scripts/deploy.sh`，既有） | 內容部署（新增） |
| :--- | :--- | :--- |
| 觸發 | 開發者手動 | 定時檢查到新 commit |
| 拉取 | 網站 repo（手動 `git pull`）＋**內容 repo 一併拉到最新** | **只拉內容 repo** |
| `npm ci` | 會 | 不會 |
| 建置、結構檢查、同步靜態網站 | 會 | 會 |
| 同步 AI 後端、重啟服務 | 會（線上占星中斷數秒） | 不會 |

**內容部署不得拉取網站 repo**：網站程式維持上次 `deploy.sh` 部署的版本，不會順帶上線尚未準備好的程式碼；開發者照現行方式推送程式即可。
例外：開發者部署了「需要新內容欄位」的程式碼時，須同時更新內容 repo，否則下一次內容部署會建置失敗（維持原站並通知）。

內容部署腳本的要求：
1. **加鎖**（`flock`）：與程式部署**共用同一把鎖**，不得同時寫入網站目錄。
2. **建置、結構檢查、同步**：兩支腳本共用同一份實作，避免日後只改一邊。
3. **合併多次發布**：檢查間隔內的多次 commit 自然合併為一次建置。Sveltia 一次發布產生「先圖、後文」兩個 commit，
   為避免剛好在中間建置：**遠端最新 commit 產生不到 1 分鐘，本輪跳過**（即使拆成兩次建置也無害：圖先到、文後到）。
4. **防呆**：內容資料夾不存在即建置失敗（第 3 小節）；同步前確認文章數不為 0；確認內容 repo 不含符號連結。
5. **建置失敗時維持原站**：先建置成功、通過結構檢查，才同步到網站根目錄。
6. **失敗不重試**：同一版本失敗後不再重建，有新 commit 才再試；同一錯誤只通知一次。
7. **記憶體上限**：VPS 無 swap，與 AI 服務共用記憶體，建置須設上限。
8. **每日強制重建**（第二階段起，下架日期需要，第五節第 6 小節）：沒有新 commit 也重建；但遠端版本已在狀態檔標為失敗時跳過（與第 6 點一致）。
9. **log 不得過濾錯誤訊息；成功與否只看本次執行結果**，不從累積的 log 找字樣（同機另一 Astro 站建置失敗 10 天未被發現的教訓）。

### 3. 內容接入方式：`CONTENT_DIR` 直接讀取（2026-11-24 定案）

建置時由 Content Collections 直接讀取旁邊的內容資料夾（`glob()` 的 `base`），不複製、不用 git submodule。
- 預設 `../starwoven-content`，路徑以程式檔位置推導，不受執行目錄影響。VPS 不設 `CONTENT_DIR`，一律走預設。
- **內容資料夾不存在即建置失敗**：Astro 預設只警告並產出「零篇文章」的網站。所有環境同一規則，不提供空內容模式。
- **不用 submodule**：其長處「版本精確鎖定」非本站需求；每次發文都須在網站 repo 更新指標 commit，違反「內容部署不碰網站 repo」。
- **不用建置前複製**：開發機也須複製，私有內容可能被誤 commit 進公開的網站 repo；另有副本過期、本機無法即時預覽的問題。
- **網站 repo 不放範例內容**：目前沒有需要的人，且範例會帶來「正式環境誤讀範例」的風險。
  易錯情況（空日期、含 HTML、`javascript:` 連結）由功能測試的測試檔涵蓋，測試檔不得作為網站內容來源。
  重新評估時機：第二位開發者加入，或要設自動檢查（CI）時。
- **本機開發注意**：開發前先 `git pull` 內容 repo；切換內容來源前先停 dev 並刪 `.astro/`（否則出現 `LocalImageUsedWrongly`）；注意 Windows／Linux 檔名大小寫差異。

### 4. 建置帳號與 VPS 資料夾（2026-11-24 定案方向，部署改造時動手）

- 建置改以非 root 專用帳號（暫名 `starwoven-build`）執行；不沿用 AI 服務帳號 `starwoven`，以免削弱服務隔離。
- `/root` 為 `drwx------`，一般帳號進不去，因此 VPS 上的 repo 搬至 `/srv/starwoven-workspace/`（選 `/srv` 而非家目錄：路徑與帳號名稱脫鉤）。搬完移除舊位置，VPS 只留一份。
- 權限分工：建置帳號負責拉取、建置、持有 deploy key；root 只做同步到 `/var/www/starwoven` 與重啟服務。
- **建置帳號與 root 的交接**（防止為了「能上架」給建置帳號過大權限，使隔離失效）：
  - 由 root 擁有、建置帳號**不可修改**的固定上架程式（腳本或 systemd unit），只把固定位置的建置產物（`/srv/.../dist/client/`）經結構檢查後同步到固定的 `/var/www/starwoven`。
  - 不接受任何參數（來源與目的地寫死）；建置帳號只能觸發它。若用 sudo，只開放這一個完整指令路徑，不得開放 `rsync`、`chown` 或整支部署腳本。
  - 正式實作時明列各檔案與資料夾的擁有者、權限，以及建置帳號可執行的指令。
- 與 B 層命名（`starwoven-app`、`/var/www/starwoven`、certbot webroot）一起設計，伺服器只動一次；
  新部署腳本與 VPS agent 的操作說明由開發端寫好後交付。最晚在開放給全部編輯者之前完成。

### 5. 建置失敗通知（2026-11-24 定案：第一階段不做即時推播）

- **主要**：編輯者發現網站未更新即回報開發窗口。教學須說明：「後台顯示『已發布』只代表存檔成功；超過 15 分鐘網站仍未更新，請通知開發窗口。」
- **輔助**：腳本維護一行**狀態檔**（最後檢查時間、最後建置時間、版本、結果、連續失敗起點）；
  VPS 的 OpenClaw agent 每日 Telegram 回報時**只讀狀態檔**，失敗才查完整 log。「最後檢查時間」停滯即代表排程停擺。
- **log**：沒有新內容時不寫 log（只更新狀態檔）；建置時完整記錄（未過濾的錯誤、建置秒數、最高記憶體、文章數，用於觀察增長趨勢）；
  寫入 systemd journal，設保留期限與容量上限（`MaxRetentionSec`、`SystemMaxUse`、`SystemKeepFree`）。journald 為全機共用設定，須確認同機其他服務的保留需求。
- 建置失敗時讀者看到上一版網站，之後所有發布（新增、修改、刪除）都會卡住，修好後一次上線。
- 日後若需要：失敗時即時推播至 Telegram。不採 Email（設定麻煩、易被當垃圾信）、GitHub Issue（需要可寫入的權杖）；LINE Notify 已於 2025 年停止服務。

## 八、圖片處理

- **repo 膨脹風險**：git 永久保存每個版本；10 位編輯者長期上傳數 MB 原圖，repo 持續變大、VPS 拉取變慢。
  方案 C 下只影響內容 repo，網站 repo 保持輕巧。
- **上傳時轉成 WebP，原檔不進 git**：轉檔必須在**提交之前**（編輯者瀏覽器內）完成。
  先提交原檔、事後轉檔刪除（例如 GitHub Actions）無效——原檔已進歷史，repo 不會變小，不採用。
  轉檔參數比照素材規範 WebP Q85，限制最大寬高（Sveltia 已驗證：Q85、最大 1920）。
- **不允許 GIF 與 SVG**（2026-11-24 定案，日後有需求再議）：GIF 不會轉 WebP，進 repo 後永久留在歷史中。
  以圖片欄位的 `accept` 在後台直接擋（只收 JPG、PNG、WebP、HEIC），不等到建置才失敗。
- **單檔大小上限**（第二道防線）：擋下 CMS 未轉檔或轉檔失敗的數 MB 原圖；建議 2～3 MB（第十二節）。大小上限擋不住 GIF，與 `accept` 兩者都要設。
- **建置時**：`astro:assets`（`image()`＋`<Image>`）產生 480／960／原寸（上限 1440）三種寬度，由瀏覽器依螢幕挑選。
  文章頁頂端封面須設 `loading="eager"`（`<Image>` 預設 lazy）。
- **建置快取**：多尺寸圖片與內容資料快取於 `node_modules/.astro/`，原圖未變即不重做。內容部署不跑 `npm ci`，快取保留；
  程式部署的 `npm ci` 會清掉。日後圖片多到程式部署變慢時，以 `cacheDir` 移出 `node_modules/`。
- **素材三分類**（圖片跟著它所屬的內容走）：版型素材（背景、圖示、404、OG、頁尾 QR、服務插圖）留網站 repo；
  內容素材（輪播海報、部落格封面、工作坊海報、影片縮圖）放內容 repo；中間地帶（團隊、課程照片）暫留網站 repo，該頁納入 CMS 時再搬。
  **圖片不得比它的資料先搬**（程式以 `/assets/...` 引用，先搬會破圖）；既有 5 篇封面隨文章搬入內容 repo 後，網站 repo 的舊檔才能刪。
- 以上仍不足時，再評估 Git LFS 或外部圖床。
- **兩套素材規範**：`AGENTS.md`「Asset management」（不得提交原始 PNG、轉 WebP Q85、人工檢查後上架、登錄 `image-prompts.md`）是為開發端素材設計的；
  CMS 上傳圖片改為建置時自動最佳化、編輯者自行檢查、不登錄 `image-prompts.md`。須於 `AGENTS.md` 明訂適用範圍。

## 九、CMS 選型：Sveltia CMS

### 1. 結論與理由
- **編輯體驗**：有台灣繁中介面（依瀏覽器語言切換）、上傳時於瀏覽器轉 WebP——直接影響不懂程式的編輯者是否願意自行操作。
- **可維護性與伺服器負載**：三個候選中最佳；在編輯者瀏覽器執行，只需一個登入轉接服務；靜態頁面＋設定檔，與 Astro 建置脫鉤；免費。
- **唯一缺點**（編輯者須持寫入權）：以方案 C 解決，方案 C 另有隱私與 repo 隔離效益（第六節）。
- **風險與退路**：尚未發布 1.0、主要由單一維護者開發。可鎖定版本自行提供，原作者停止維護既有版本照樣能用；
  設定檔格式與 Decap CMS 相容，必要時改用 Decap；內容是 repo 中的普通檔案，換任何 Git-based CMS 都不必搬資料，只要重寫設定檔。
- 備案 Pages CMS：2026-11-24 驗證通過，不啟用。
- 三方比較表與 v0.1 評估條件見驗證紀錄。

### 2. 登入轉接服務（2026-11-24 已架設）
- 採官方 `sveltia-cms-auth`，部署於 Cloudflare Workers 免費方案（`sveltia-cms-auth.unendless314.workers.dev`；程式副本在私有 repo `unendless314/sveltia-cms-auth`）。
- GitHub App `Starwoven Studio CMS`（屬 `starwoven-studio`）：權限只有 Contents 讀寫＋Metadata 唯讀（不開 Pull requests，本站不設審核）；不產生 private key；只安裝在內容 repo。
- Worker 變數全部設為 Secret（Text 類型會在自動部署時被覆蓋清掉）；`ALLOWED_DOMAINS` 正式上線後評估移除 `localhost`。
- 後台若突然無法登入，先檢查 workers.dev 網址是否被自動部署關閉、Secret 是否還在。
- **觀察項目**：Sveltia CMS Additions（2026-11-22 才發布 v1.0）另提供帳號密碼登入（**編輯者不需 GitHub 帳號**）、角色權限等；
  數個月後若穩定再評估改用（官方有遷移說明，內容不受影響）。

### 3. 未採用（各一句理由，詳見驗證紀錄）
- **Pages CMS**：線上版單點故障且第三方持有 repo 寫入權；自架須在 VPS 常駐 Next.js＋PostgreSQL，這台 VPS 同時是正式機、建置機與抽卡主機，不宜再加常駐服務。
- **Keystatic**：須加入 React（違反「不用 JS 框架」）、後台成為 Node 服務的新對外入口、Astro 新版支援可能落後而卡住安全更新、只有英文介面。
- **Decap CMS**：Sveltia 即為其改良版；Decap 託管服務 Turbo 須付費且尚在預覽。
- **TinaCMS**：自架複雜，主要功能依賴付費雲端服務。
- **自行開發 CMS 後台**：只採用既有開源方案。

## 十三、正式開放給編輯者前必須處理的問題

技術驗證（2026-11-24）發現的問題；實測經過與數據見驗證紀錄。

1. **選填欄位留空會讓建置失敗**：Sveltia 對空白欄位寫入 `''`。schema 須把 `''` 視同未填（spike 已示範），所有選填日期／數字欄位比照；並查 Sveltia 是否有「空值不寫出」設定。
2. **內文插圖會破圖，且建置抓不到**（**最優先**）：插圖存到全站 `/media/` 而非文章的 `images/`，且編輯器輸出 HTML（`<figure><a><img>`），Astro 不處理 → 線上 404。
   須指定內文欄位的圖片資料夾、限制編輯器只產生 Markdown 圖片（不含連結／圖說）；並在建置時檢查「內文引用的圖片是否存在」，不存在即建置失敗（2026-11-24 定案）。與第六節「內文不得含原始 HTML」一起處理。
3. **動畫 GIF 不轉檔**：不允許 GIF，以 `accept` 在後台擋，並設單檔大小上限（第八節）；寫進教學。
4. **上傳檔名保留原名**（如 `IMG_20260705_185236_1.webp`，含 `_`）：開啟 Sveltia 的 `slugify_filename: true`
   （設於 `media_libraries`，轉小寫、空格與無效字元換成 `-`）。官方文件未說明底線是否被替換，推測會保留；實作時實測，若仍在，再決定是否將 CMS 上傳圖片列為命名規則例外。
5. **一次發布產生兩個 commit**（先圖、後文）：由定時檢查合併，並以「最新 commit 不到 1 分鐘則跳過」避開中間狀態（第七節第 2 小節第 3 點）。
6. 照片 1440×1920 仍有 601 KB：可考慮最大寬高降到 1600；Astro 會再壓縮，非必要。
7. **Slug 須手動輸入英數**，輸入中文或空格會被擋（錯誤訊息為英文）：寫進教學，或改為自動產生（如日期＋短碼）。
8. **YouTube 專門欄位待決細節**：直式／橫式判斷（可依 `/shorts/` 網址）、放置位置、一篇幾支、是否保留網址中的起始時間（`t=`，只接受數字秒數）；影片多的頁面採「先顯示封面圖、點擊才載入播放器」。
9. **HEIC 未驗證**：以 iPad（相機格式設「高效率」）在 Safari 後台直接從相簿上傳補測；iPadOS 若先自動轉成 JPG，也一併記錄。
10. **清除測試殘留**：內容 repo 的測試 commit（`cms-test-1` 文章、照片、GIF）於邀請編輯者前刪除（刪檔或刪 repo 重建皆可）；`public/admin/config.yml` 的 `site_domain: localhost` 正式版移除。
