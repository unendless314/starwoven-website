> **文件狀態**：v0.3 草稿（2026-11-24），**尚未實作**。
> - 2026-11-23 選型方向已定：**Sveltia CMS ＋ 內容獨立 repo（方案 C）**（第六、九節）。
> - 2026-11-24 技術驗證通過，方案 C 成立（第十三節）；同日定案內容安全措施（第六節）、內容接入方式與部署觸發、失敗通知（第七節）。
> - 架構決策已登錄 **DEC-092**（2026-11-24）；`AGENTS.md` 於正式實作時同步（第十節）。
>
> **沿革摘要**：業主經常要求更新交流會場次、工作坊、首頁輪播海報，日後還要發布部落格文章、新增影片頁。現行流程是業主傳訊、開發者請 AI 改程式碼、再部署到 VPS，速度慢，也容易出錯或漏改。開發者與 AI 討論後，曾考慮比照星靈出攤改用 Google 試算表加 VPS 定時重建，後因部落格長文與影片頁的需求，改採 Git-based CMS。
> **核心目標**：**誰要改內容，就由誰負責**。業主方編輯者在網頁後台自行發布，發布後自動上線；開發端只負責系統穩定，不經手內容。
> **長期目標**：業主方全部內容營運皆在 CMS 自行維護。**但不強迫使用者一開始就改變既有習慣**，分階段遷移（第三節）。

## 一、設計原則

1. **職責分工**：
   - 內容品質由業主方負責，開發端不審查內容。
   - 發布後直接上線，不設審核流程（開發窗口 2026-11-17 確認）。
2. **商業營運優先於技術一致性**：
   - 一項內容要不要遷移，看它**是否正在妨礙營運**，而不是技術上是否整齊。
   - 運作正常、使用者已經習慣的系統（星靈出攤）延後遷移。
3. **內容於建置時寫入 HTML**：
   - 搜尋引擎可以收錄。
   - 訪客打開頁面時不需要即時讀取外部服務，沒有載入等待。
   - 網頁顯示不依賴 Google。
4. **壞掉也不能讓網站變糟**：建置失敗時，網站維持上一版內容，並通知開發者（第七節）。
5. **表單先擋錯**：
   - 能用必填欄位、日期選擇器、下拉選單擋住的錯誤，就在後台擋。
   - 建置時再以 Content Collections schema 做第二道驗證。
6. **紀錄可追溯**：
   - 每次發布都是一筆 git commit，記下發布者、時間與改動。
   - 改壞了可以還原到前一版。
7. **先有畫面，再做模組**：
   - 新的內容類型，先以寫死資料的版型給業主確認，開發端維護內容。
   - 業主確認畫面後，才做 CMS 模組。
   - 理由：沒有參考物就先定下 CMS 欄位，日後改版面時，後台欄位與已發布的內容都要一起改。
   - 部落格與工作坊的畫面已上線並經業主檢驗，不受此限。

| # | 問題 | 判斷 |

## 三、分階段範圍

排序原則：**先做業主「原本做不到、現在自己能做」的項目，最後才動他們已經習慣的工具。**

### 第一階段：部落格、主題工作坊
- 這兩項目前都要找開發者修改，業主沒有既定操作習慣。CMS 對他們是新增能力，不是改變習慣。
- 同時用來驗證整套流程：編輯者登入、發布、自動部署、建置失敗通知。
- 這一階段順帶完成編輯者的 GitHub 帳號申請與教學（開發窗口負責）。

### 第二階段：交流會場次、輪播海報、影片頁
- 交流會與輪播海報需要「下架日期」（第五節第 6 小節）。
- **影片頁依第一節第 7 點，分兩步**：
  1. **版型（不依賴 CMS，可提前進行）**：
     - 影片資料寫在頁面程式碼開頭的資料陣列（比照現行工作坊），由開發端維護。
     - 欄位比照第五節第 5 小節設計，日後搬成內容檔案時不必改版面。
     - 頁面設 `noindex`、不加入導覽列，以直接網址給業主確認（比照 `/tarot`，DEC-073）。
  2. **CMS 模組**：業主確認版型後，決定導覽列名稱與位置、立 DEC（新路由屬 IA 變更），再把資料陣列遷移為 CMS 內容。

### 第三階段：星靈出攤
- 現行試算表使用頻率高、業主已經用熟。編輯者熟悉 CMS 後再遷移，以免引起反彈、因小失大。
- 遷移後退役 `PUBLIC_BOOTH_API_URL` 與出攤用的 Apps Script，並改寫 `booth-plan.md`。
- **時效性的變化**：現行做法是業主改完、訪客重新整理就生效；遷移後為發布後數分鐘生效。遷移前須確認業主可以接受。

### 第四階段：課程許願池（視使用情況決定）
- 截至 2026-11-17 尚無人投票，載入慢（約 2～3 秒，Apps Script 冷啟動加 302 轉址）目前不構成營運問題。
- **若遷移**：
  - 課程清單 → CMS。
  - 投票 → VPS Node 服務新增投票 API，搭配 SQLite（沿用 DEC-073 架構）。
- **已確認的簡化規則**：
  - 票數不重要，換課時票數從 0 開始計算，以 CMS 課程編號為鍵，不搬遷舊票。
  - 因此不需要嚴謹的備份機制。
- **不採部分遷移**：不只搬課程清單、投票留在試算表，以免兩邊課名不一致導致計票錯誤。
- **若長期無人使用**：請業主評估這個功能是否保留，或改成「想上這門課，私訊我們」的 LINE 按鈕。屬商業判斷。

## 五、內容模型（初稿）

> 下列欄位為初稿，實作前逐項與開發窗口確認。內容檔存放於內容 repo（第六節），建置時接入網站，以 Content Collections schema 驗證。

### 1. 部落格（既有 `blog` collection）
- 沿用既有 schema（`src/content.config.ts`）與 `BLOG_CATEGORIES`。
- **待改**：`coverImage` 目前是 `public/assets/` 的路徑字串，不會經過圖片最佳化。
  - 改為 `astro:assets` 的 `image()` 後，編輯者上傳的圖片才能在建置時自動轉成 WebP 並縮圖（第八節）。
  - 既有 5 篇文章的封面要一併搬移。
- 現行規範「文章不寫死課程星期、時段、講師、價格，一律連到 `/courses#recurring`」：須寫進編輯者教學。

### 2. 主題工作坊（新 collection，取代 `courses.astro` 的 `workshops` 陣列）
- 欄位：
  - 標題、副標、標籤、講師
  - 時間（自由文字）、費用、費用附註
  - 課程簡介、學習重點（0～3 條）、適合對象、課綱（選填，多日課用）
  - YouTube 網址：貼完整網址，程式取出影片編號；留空時顯示「短影音籌備中」
  - 排序、下架日期
- 卡片代碼（課程-H、課程-K 等）：由程式產生，或改為不顯示。待決。

### 3. 交流會場次（第二階段）
- 欄位：日期、時間、下架日期（可預設為當天）。
- 交流會的費用與說明文字變動頻率低：放 CMS 的「單一設定」頁，或維持寫在程式碼裡。待決。

### 4. 首頁輪播海報（第二階段）
- 欄位：海報圖片、替代文字（必填，無障礙用）、連結（預設為官方 LINE）、排序、下架日期。
- 「光之編織」品牌保底圖（DEC-086）維持寫在程式碼中，不交給 CMS，確保輪播永遠至少有一張。

### 5. 影片頁（第二階段，新路由）
- 欄位（初稿，業主確認版型後定案）：標題、YouTube 網址、分類（選填）、發布日期、簡介（選填）。
- 先做版型、再做模組（第三節第二階段）；頁面設計另立規格。

### 6. 下架日期的處理（靜態網站的限制）
網頁是建置時產生的，日期過了，HTML 不會自己改變。以兩種方式並用：
1. **每日凌晨自動重建一次**：過期項目從 HTML 移除。
2. **前端比對日期**：瀏覽器打開網頁時，再比對一次日期、隱藏已過期的項目，補足重建前的空窗。
- 下架日期採日期選擇器，不開放自由文字，避免格式錯誤。
- 時區以台灣時間（UTC+8）為準。

## 六、編輯者權限（2026-11-23 方向已定：方案 C）

**問題**：
- 多數 Git-based CMS 以 GitHub 帳號登入，編輯者必須擁有 repo 的寫入權限。
- **有寫入權就能修改整個網站的程式碼**，不只是內容。
- 預計約 10 位編輯者。只要有一人透過 GitHub 網頁誤操作，就可能刪除或改壞程式。

**三個候選解法與評估結果**：

| 方案 | 說明 | 結果 |
| :--- | :--- | :--- |
| A. CMS 自有登入 | 編輯者登入 CMS，由 CMS 代為提交；編輯者不持有 repo 寫入權 | 可行的 CMS（Pages CMS、付費雲端版）各有缺點，見第九節。不採用 |
| B. GitHub 路徑限制 | 編輯者持有寫入權，以 push ruleset 限制只能修改內容路徑 | **不可行**：push ruleset 只開放給付費 Team 方案的私有 repo；本 repo 為免費個人帳號的公開 repo |
| C. 內容獨立 repo | 內容放在另一個 repo，建置時接入網站 | ✅ **採用** |

**不採「同一 repo 的內容分支」**：GitHub 寫入權以整個 repo 為單位，編輯者可以推送到任何分支，包括修改 GitHub Actions workflow；修改後的 workflow 執行時可能讀到 repo 裡的機密（例如部署金鑰）。

### 方案 C 的架構

- **網站 repo**（現有，公開）：程式碼，只有開發者有寫入權。
- **內容 repo** `starwoven-studio/starwoven-content`（2026-11-24 已建立）：
  - 只放 CMS 管理的內容檔與圖片；編輯者只拿到這個 repo 的寫入權。
  - **設為私有**：免費方案的私有 repo 也能邀請協作者。
  - **建立在免費的 GitHub 組織 `starwoven-studio` 之下**，而非開發者個人帳號
    （`starwoven` 已被他人使用；名稱不綁 `.xyz` 網域，因網域日後可能更換）：
    - 組織設定：Base permissions＝No permission、成員不得建立 repo。
    - 日後業主接手時，只要把業主加為組織擁有者，repo 路徑與設定都不用改。
    - 換人維護時，新開發者加入、原開發者退出即可。
    - 網站 repo 日後也可移入同一組織。
    - 2027 年公司註冊後，組織改為企業歸屬，並把業主加為擁有者。

### 內容 repo 的安全措施（2026-11-24 定案）

前提：**編輯者帳號可能被盜**。目標是帳號出事時，損害只限於「內容被亂改」（可從 git 歷史還原），
不得擴及訪客、伺服器與機密。判斷原則：**能復原的壞掉從簡處理；不能復原的（資安、外洩）事先防範。**

1. **只接受 `.md`，不接受 `.mdx`**：MDX 可在建置時執行程式。Content Collections 只讀 `*.md`，Sveltia 設定 `extension: md`。
2. **內文不得含原始 HTML**：`.md` 的原始 HTML（`<script>`、`<iframe>`、`onerror=` 等）會原樣輸出，在訪客瀏覽器執行。
   - 以 Markdown 解析結果檢查（**不用字串比對**，寫法變化太多）：出現任何原始 HTML 節點 → **建置失敗**（不默默刪除），網站維持上一版。
   - 連結與圖片網址只允許 `https://`、`mailto:`、站內路徑（擋 `javascript:` 等）。
   - 須先解決 Sveltia 插圖輸出 HTML 的問題（第十三節第 2 點），否則編輯者正常操作就會建置失敗。
   - YouTube 改用專門欄位（第五節第 2、5 小節），程式只取影片編號、自行產生播放框。
   - CSP（瀏覽器端第二道防線）暫不做。
3. **Sveltia 設定檔放在網站 repo**（`public/admin/config.yml`）：編輯者改不到表單驗證；表單與 `content.config.ts` 同 repo、一起改一起上線。
   該檔必然公開（瀏覽器須讀取），**不得放任何密碼或金鑰**。網站 repo 維持公開（2026-11-24 掃描全部歷史，未發現機密）。
4. **VPS 以唯讀 deploy key 拉取內容 repo**：只開這一個 repo、唯讀、不綁個人；不用個人權杖。
   鑰匙由建置帳號產生、不得進任何 repo；列入第十二節第 15 項歸屬清單（位置、外洩時更換步驟）；重建 VPS 時須重新產生並登記。
5. **以非 root 專用帳號建置**（第七節第 4 小節）：圖片處理程式若有漏洞，特製圖片可能在建置時執行程式；
   專用帳號讀不到 `/etc/starwoven/app.env` 與同機其他服務。
6. **建置前檢查內容 repo 不含符號連結**：防止以捷徑檔讀取伺服器上的機密檔。
7. **組織強制成員開啟兩步驟驗證**：正式邀請編輯者時開啟，降低帳號被盜機率。

技術上無法防範的：帳號被盜後改寫文字、放詐騙連結、換圖片。靠兩步驟驗證、git 歷史還原與編輯者教學（不貼來路不明的連結與嵌入碼）。

### 方案 C 的效益

- **權限隔離**：編輯者誤操作最多影響內容，碰不到程式碼。
- **隱私**：內容 repo 為私有，下列 v0.1 因 repo 公開而擔心的問題不再成立：
  - 編輯者帳號名稱公開。
  - 誤貼個資永久公開。
  - 草稿公開。
- **仍須教學**：提交過的內容仍會永久留在內容 repo 的歷史紀錄中，只是不公開；誤貼個資仍列為教學重點。
- **repo 膨脹隔離**：編輯者上傳的圖片只會讓內容 repo 變大，網站 repo 不受影響（第八節）。
- **分支策略問題自然消失**（第七節第 6 小節）。

### 方案 C 的代價（皆在開發端）

- 建置與本機開發都要先取得內容 repo，接入網站（第七節第 3 小節）。
- 既有內容要搬家：部落格 5 篇文章與封面。
- 開發者修改內容欄位（schema）時，要同步更新內容 repo 內的檔案；不符合的內容會在建置時被 schema 驗證擋下，不會默默壞掉。

### Repo 拆分原則（2026-11-23 討論結論，適用於日後所有模組）

方案 C 讓專案從一個 repo 變成兩個。日後新增論壇、購物等功能時，依同一原則判斷要不要另開 repo：

- **依「部署或權限的邊界」拆，不依「功能」拆，也不提前拆。** 符合下列任一項才拆：
  1. 由不同的人修改（例：內容由編輯者修改 → 拆成內容 repo）。
  2. 部署方式或時機不同（例：需要常駐伺服器的論壇、購物後台）。
  3. 技術完全不同。
- **資料庫不做成獨立的共用模組**：資料庫屬於使用它的服務。各模組共用同一個資料庫，等於重新綁在一起。
- **AI 抽卡服務現階段不拆**：
  - 前台頁面使用網站共用的版型與主題，本來就屬於網站；真正可能拆出去的只有後端 API。
  - 目前前台與 API 共用 `src/lib/ai/shared/`，同一位開發者主導，流量不大；拆開後要多維護一套建置與部署，前後端改動也要分開協調，效益不明顯。
  - **重新評估的時機**：新功能需要會員帳號、付費或儲存使用者資料（需要資料庫）、改由不同開發者負責、部署互相干擾到影響營運，或需要不同的技術或機器。功能「數量」變多本身不構成理由。
  - **預留拆分的可能**：新增 AI 功能時遵守 `ai-platform-plan.md` 第十節的檢查清單（伺服器程式放在 `server` 資料夾、前端不得 import、各功能互不 import），日後要拆就是整個資料夾搬出去。

**資料夾結構**（開發機與 VPS 內部相同，外層位置不同）：

```
starwoven-workspace/        ← 上層工作資料夾，本身不是 git repo（避免巢狀 git）
├── starwoven-website/      ← 網站 repo
└── starwoven-content/      ← 內容 repo（方案 C）
```

- 開發機：`C:\Users\user\Documents\starwoven-workspace\`。
- VPS：現為 `/root/.openclaw/workspace/starwoven-workspace/`；部署改造時搬至 `/srv/starwoven-workspace/`（第七節第 4 小節）。
- 跨 repo 一律用相對路徑，外層搬移時程式不必修改。接入方式見第七節第 3 小節。

## 七、部署流程

### 1. 流程
```
編輯者在後台按「發布」
  → CMS 提交 commit 到內容 repo
  → VPS 每 5 分鐘檢查一次（systemd timer），發現新 commit
  → VPS：拉取內容 repo → 建置 → 結構檢查 → 同步靜態網站
  → 約 6～7 分鐘內上線（最多等一輪檢查＋可能跳過一輪的 1 分鐘＋建置時間）
```

**觸發方式：VPS 定時檢查（2026-11-24 定案）**
- **不用 GitHub Actions**：設定檔須放在內容 repo，編輯者有寫入權，可改寫設定檔竊取存放在 GitHub 的 VPS 登入鑰匙。
- **不用 webhook（暫不需要）**：VPS 須對外開放接聽網址並正確驗證簽章，多一段要維護、可能寫錯的程式。
- 定時檢查只由 VPS 往外連，不開新的對外入口，也不在 GitHub 存放 VPS 的鑰匙。
- 間隔 5 分鐘：每次先以 `git ls-remote` 比對版本號（數 KB），有新 commit 才拉取與建置；
  建置次數取決於發文量，與間隔無關。日後嫌慢，可加 webhook 呼叫同一支腳本，其餘不變。
- systemd timer 設定：輪詢 timer 設 `AccuracySec=1s`（預設 1 分鐘，會延後觸發）；每日重建 timer 用 `OnCalendar=` 加 `Persistent=true`（VPS 關機錯過時，開機後補跑）。

### 2. 兩套部署腳本

| | 程式部署（`scripts/deploy.sh`，既有） | 內容部署（新增） |
| :--- | :--- | :--- |
| 觸發 | 開發者手動 | 定時檢查到新 commit |
| 拉取 | 網站 repo（手動 `git pull`）＋**內容 repo 一併拉到最新** | **只拉內容 repo** |
| `npm ci` | 會 | 不會 |
| 建置、結構檢查、同步靜態網站 | 會 | 會 |
| 同步 AI 後端、重啟服務 | 會（線上占星中斷數秒） | 不會 |

內容部署**不得拉取網站 repo**：網站程式碼維持上次以 `deploy.sh` 部署的版本，內容部署不會順帶上線尚未準備好的程式碼。

內容部署腳本的要求：
1. **加鎖**（`flock`）：與程式部署**共用同一把鎖**，不得同時寫入網站目錄。
2. **建置、結構檢查、同步**：兩支腳本共用同一份實作，避免日後只改一邊。
3. **合併多次發布**：檢查間隔內的多次 commit 自然合併為一次建置。Sveltia 一次發布會產生「先圖、後文」兩個 commit，
   為避免剛好在兩者之間建置：**遠端最新 commit 若產生不到 1 分鐘，本輪跳過，下一輪再建**。
   （即使仍拆成兩次建置也無害：圖先到、文後到，中間那次不會壞。）
4. **防呆**：內容資料夾不存在即建置失敗（第 3 小節）；同步前確認文章數不為 0；確認內容 repo 不含符號連結。
5. **建置失敗時維持原站**：先建置成功、通過結構檢查，才同步到網站根目錄。
6. **失敗不重試**：同一版本失敗後不再重建，有新 commit 才再試；同一錯誤只通知一次。
7. **記憶體上限**：VPS 無 swap，與 AI 服務共用記憶體，建置須設上限。
8. **每日強制重建一次**（第二階段起）：下架日期需要（第五節第 6 小節），即使沒有新 commit 也要重建。
   但**遠端版本已在狀態檔標為失敗時跳過**（與第 6 點一致），直到出現新 commit。
9. 參照同機另一 Astro 站的教訓（建置失敗 10 天未被發現）：**log 不得過濾錯誤訊息**；成功與否只看本次執行結果，不從累積的 log 找字樣。

### 3. 內容接入方式：`CONTENT_DIR` 直接讀取（2026-11-24 定案）

建置時由 Content Collections 直接讀取旁邊的內容資料夾（`glob()` 的 `base`），不複製、不用 git submodule。

- 預設 `../starwoven-content`，路徑以程式檔位置推導，不受執行指令的目錄影響。VPS 不設 `CONTENT_DIR`，一律走預設。
- **內容資料夾不存在即建置失敗**：Astro 預設只警告並產出「零篇文章」的網站。所有環境同一規則，不提供空內容模式。
- **不用 submodule**：其長處「版本精確鎖定」非本站需求；每次發文都須在網站 repo 更新指標 commit，違反「內容部署不碰網站 repo」。
- **不用建置前複製**：開發機也須複製，私有內容可能被誤 commit 進公開的網站 repo；另有副本過期、本機無法即時預覽的問題。
- **網站 repo 不放範例內容**：目前沒有需要的人，且範例會帶來「正式環境誤讀範例」的風險。
  容易出錯的情況（空日期、含 HTML、`javascript:` 連結）改由功能測試的測試檔涵蓋，測試檔不得作為網站內容來源。
  重新評估時機：第二位開發者加入，或要設自動檢查（CI）時。
- 本機開發注意：開發前先 `git pull` 內容 repo；切換內容來源前先停 dev 並刪 `.astro/`；注意 Windows／Linux 檔名大小寫差異。
- 開發者修改內容欄位（schema）時，須同步更新內容 repo（第 6 小節）。

### 4. 建置帳號與 VPS 資料夾（2026-11-24 定案方向，部署改造時動手）

- 建置改以非 root 專用帳號（暫名 `starwoven-build`）執行；不沿用 AI 服務帳號 `starwoven`，以免削弱服務隔離。
- `/root` 權限為 `drwx------`，一般帳號進不去，因此 VPS 上的 repo 搬至 `/srv/starwoven-workspace/`
  （選 `/srv` 而非帳號家目錄：路徑與帳號名稱脫鉤）。搬完後移除舊位置，VPS 只留一份。
- 權限分工：建置帳號負責拉取、建置、持有 deploy key；root 只做同步到 `/var/www/starwoven` 與重啟服務。
- **建置帳號與 root 的交接**（防止為了「能上架」而給建置帳號過大權限，使隔離失效）：
  - 由 root 擁有、建置帳號**不可修改**的固定上架程式（腳本或 systemd unit），只做一件事：
    把固定位置的建置產物（`/srv/.../dist/client/`）經結構檢查後同步到固定的 `/var/www/starwoven`。
  - 不接受任何參數（來源與目的地寫死）；建置帳號只能觸發它，不能用它執行其他指令。
    若用 sudo，只開放這一個完整指令路徑，不得開放 `rsync`、`chown` 或整支部署腳本。
  - 正式實作時明列各檔案與資料夾的擁有者、權限，以及建置帳號可執行的指令。
- 與 B 層命名（`starwoven-app`、`/var/www/starwoven`、certbot webroot）一起設計，伺服器只動一次；
  新的部署腳本與 VPS agent 的操作說明由開發端寫好後交付。最晚在開放給全部編輯者之前完成。

### 5. 建置失敗通知（2026-11-24 定案：第一階段不做即時推播）

- **主要**：編輯者發現網站未更新即回報開發窗口。教學須說明：「後台顯示『已發布』只代表存檔成功；超過 15 分鐘網站仍未更新，請通知開發窗口。」
- **輔助**：腳本維護一行**狀態檔**（最後檢查時間、最後建置時間、版本、結果、連續失敗起點）；
  VPS 上的 OpenClaw agent 每日 Telegram 回報時**只讀狀態檔**，失敗才查完整 log。「最後檢查時間」停滯即代表排程停擺。
- **log**：沒有新內容時不寫 log（只更新狀態檔）；建置時完整記錄（未過濾的錯誤、建置秒數、最高記憶體、文章數，用於觀察增長趨勢）；
  寫入 systemd journal，並設保留期限與容量上限（journald 的 `MaxRetentionSec`、`SystemMaxUse`、`SystemKeepFree`）。
  注意 journald 為全機共用設定，會一併影響同機其他服務的 log，設定時須確認其他服務的保留需求。
- 建置失敗時讀者看到的是上一版網站，之後所有發布（新增、修改、刪除）都會卡住，修好後一次上線。
- 日後若需要：失敗時即時推播至 Telegram。不採 Email（設定麻煩、易被當垃圾信）、GitHub Issue（需要可寫入的權杖）；LINE Notify 已於 2025 年停止服務。

### 6. 對開發者工作方式的影響（方案 C 已解決）
v0.1 擔心的問題：CMS 與開發者共用同一個 repo 的 `main`，開發者推上未準備部署的程式碼，會被下一次內容部署一起拉下來。

採用方案 C 後，內容提交不進網站 repo，內容部署也不拉取網站 repo（第 2 小節），開發者維持現行工作方式即可。

仍須注意：開發者部署了「需要新內容欄位」的程式碼時，要同時更新內容 repo，否則下一次內容部署會建置失敗（維持原站並通知）。

## 八、圖片處理

- **repo 膨脹風險**：git 會永久保存每個版本。10 位編輯者長期上傳數 MB 的原圖，repo 會持續變大，VPS 拉取也會變慢。
- **目標做法：上傳時轉成 WebP，原檔不進 git**。
  - **關鍵前提：轉檔必須發生在提交之前**，也就是在編輯者的瀏覽器裡、發布前完成。
  - 若先提交原檔、事後再轉檔並刪除（例如 GitHub Actions），原檔已存入歷史紀錄，**repo 不會變小**。此做法無效，不採用。
  - 轉檔參數比照現行素材規範（WebP Q85），並限制最大寬度。
  - 此功能列為 CMS 選型條件（第九節第 5 點）。2026-11-24 驗證：Sveltia 上傳時於瀏覽器轉 WebP（Q85、最大 1920），
    手機照片（JPG）→ 1440×1920 WebP（601 KB）。**動畫 GIF 不轉檔**，原樣存入（第十三節第 3 點）。
  - **不允許 GIF**（2026-11-24 定案，日後有需求再議）：GIF 不會轉 WebP，進 repo 後永久留在歷史中。
    以圖片欄位的 `accept` 在後台直接擋（只收 JPG、PNG、WebP、HEIC），不等到建置才失敗；SVG 也不收。
- **方案 C 的隔離效果**：圖片存在內容 repo，即使膨脹也只影響內容 repo，網站 repo 保持輕巧。
- **第二道防線**：設定單檔大小上限，在 CMS 未轉檔或轉檔失敗時，擋下數 MB 的原圖。
- 建置時，`astro:assets`（`image()`＋`<Image>`）再產生 480／960／原寸（上限 1440）三種寬度，由瀏覽器依螢幕挑選；
  實測手機版封面 13～23 KB（原檔 78～148 KB）。文章頁頂端封面須設 `loading="eager"`（`<Image>` 預設 lazy）。
- **建置快取**：多尺寸圖片與內容資料快取於 `node_modules/.astro/`，原圖未變即不重做。內容部署不跑 `npm ci`，快取會保留；
  程式部署的 `npm ci` 會清掉快取。日後圖片多到程式部署變慢時，以 `cacheDir` 設定移出 `node_modules/`。
- **素材三分類**（圖片跟著它所屬的內容走）：版型素材（背景、圖示、404、OG、頁尾 QR、服務插圖）留網站 repo；
  內容素材（輪播海報、部落格封面、工作坊海報、影片縮圖）放內容 repo；中間地帶（團隊、課程照片）暫留網站 repo，該頁納入 CMS 時再搬。
  **圖片不得比它的資料先搬**（程式以 `/assets/...` 引用，先搬會破圖）。既有 5 篇部落格封面隨文章搬入內容 repo 後，網站 repo 的舊檔才能刪。
- 若以上仍不足，再評估 Git LFS 或外部圖床。
- **與現行素材規範的衝突**（`AGENTS.md`「Asset management」）：
  - 「不得提交原始 PNG」「轉 WebP Q85」「人工檢查後才上架」「登錄 `image-prompts.md`」，都是為開發端素材設計的。
  - CMS 上傳的圖片改為：建置時自動最佳化，編輯者自行檢查，不登錄 `image-prompts.md`。
  - 須於 `AGENTS.md` 明訂兩套規範的適用範圍。

## 九、CMS 選型（2026-11-23 方向已定：Sveltia CMS）

> 下列比較依 2026-11-23 的網路調查整理，部分資料來自第三方比較網站。版本、價格與功能細節以官方文件及技術驗證結果為準。

### 1. 結論：採用 Sveltia CMS ＋ 方案 C

| 面向 | Sveltia | Pages CMS | Keystatic |
| :--- | :--- | :--- | :--- |
| 編輯者權限 | 需 GitHub 帳號與寫入權 → 以方案 C 隔離 | ✅ 原生方案 A：Email 邀請登入，由 CMS 代為提交 | GitHub 模式需寫入權；付費雲端版免 |
| 繁中介面 | ✅ 有台灣繁中，依瀏覽器語言自動切換 | 應無（未確認） | ❌ 只有英文 |
| 圖片轉 WebP | ✅ 上傳時於瀏覽器轉檔 | 未查到 | ❌ 原圖進 repo；付費雲端版才有圖片處理 |
| 伺服器負載 | ≈ 0：在編輯者瀏覽器執行，只需一個登入轉接服務 | 線上版 0；自架需常駐 Next.js ＋ PostgreSQL | 後台跑在網站的 Node 服務上 |
| 開發端維護 | 靜態頁面＋設定檔，與 Astro 建置脫鉤 | 線上版免維護；自架要長期維護應用程式與資料庫 | 需加入 React、Markdoc；曾有 Astro 新版支援落後的回報 |
| 單點故障 | 可鎖定版本、自行提供；原作者停止維護，既有版本照樣能用 | 線上版停機即不能發布，且第三方持有 repo 寫入權 | 雲端版依賴第三方 |
| 費用（約 10 人） | 免費 | 免費 | 3 人以上須付費 |

**採用理由**：
- 編輯體驗：繁中介面與自動轉檔兩項，直接影響不懂程式的編輯者是否願意自行操作。
- 可維護性與伺服器負載：都是三者最佳。
- 唯一缺點（寫入權）：以方案 C 解決，且方案 C 本身另有隱私與 repo 隔離的效益（第六節）。

**風險與退路**：
- 尚未發布 1.0 版，主要由單一維護者開發。
- 退路：設定檔格式與 Decap CMS 相容，必要時可改用 Decap。
- 內容為 repo 中的普通檔案，更換任何 Git-based CMS 都不必搬資料，只要重寫設定檔。

**備案**：若技術驗證發現方案 C 的建置整合過於複雜，改評估 Pages CMS（原生解決寫入權）。→ 2026-11-24 驗證通過，備案不啟用。

**登入轉接服務（2026-11-24 已架設）**：
- 採官方 `sveltia-cms-auth`，部署於 Cloudflare Workers 免費方案（`sveltia-cms-auth.unendless314.workers.dev`；
  程式副本在私有 repo `unendless314/sveltia-cms-auth`）。
- GitHub App `Starwoven Studio CMS`（屬 `starwoven-studio`）：權限只有 Contents 讀寫＋Metadata 唯讀（不開 Pull requests，本站不設審核）；
  不產生 private key；只安裝在內容 repo。
- Worker 變數全部設為 Secret（Text 類型會在自動部署時被覆蓋清掉）；`ALLOWED_DOMAINS` 正式上線後評估移除 `localhost`。
- 後台若突然無法登入，先檢查 workers.dev 網址是否被自動部署關閉、Secret 是否還在。
- **觀察項目**：Sveltia CMS Additions（2026-11-22 發布 v1.0）另提供帳號密碼登入（**編輯者不需 GitHub 帳號**）、角色權限等；
  數個月後若穩定再評估改用（官方有遷移說明，內容不受影響）。

### 2. 未採用

- **Pages CMS**：
  - 線上版有單點故障，且第三方服務持有 repo 寫入權。
  - 自架須在 VPS 常駐 Next.js 與 PostgreSQL；這台 VPS 同時是正式機、建置機與抽卡服務主機，不宜再增加常駐服務。
- **Keystatic**：
  - 違反 AGENTS.md「不用 JS 框架」（須加入 React）。

### 驗證 A：建置接入（✅）

  iPadOS 上傳時可能先自動轉成 JPG，若如此也一併記錄。

**正式開放給編輯者前必須處理的問題**：
1. **選填日期留空會讓建置失敗**：Sveltia 對空白欄位寫入 `''`。schema 須把 `''` 視同未填（spike 已示範），所有選填日期／數字欄位比照；並查 Sveltia 是否有「空值不寫出」設定。
2. **內文插圖會破圖，且建置抓不到**（**最優先**）：插圖存到全站 `/media/` 而非文章的 `images/`，且編輯器輸出 HTML（`<figure><a><img>`），Astro 不處理 → 線上 404。
   須指定內文欄位的圖片資料夾、限制編輯器只產生 Markdown 圖片；與第六節「內文不得含原始 HTML」一起處理。
3. **動畫 GIF 不轉檔**（測試檔 976 KB 原樣存入）：**不允許 GIF**，以 `accept` 在後台擋（第八節）；上傳上限改為 2～3 MB。

4. **上傳檔名保留原名**（如 `IMG_20260705_185236_1.webp`，含 `_`）：開啟 Sveltia 的 `slugify_filename: true`
